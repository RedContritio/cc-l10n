# Claude Code 的"ABC 腔"：一次长对话中的语言漂移实测

## 现象

你让 Claude Code 用中文回复。开头几轮它确实在说中文：

> 用户明确要求 agent-driven 并行执行 + TDD（测试按目的写）。先调相关 skill 取流程。

技术术语保留英文，句式和连接词是中文——正常的技术交流。

六小时后，同一个对话里它变成了这样：

> User 选 worktree 隔离 + smoke verify Phase 4 + r010-012 async + mcts 单 implementer。先看 worktree skill SOP。

> Dispatch ζ implementer：inline `legacy.config` + `legacy.train_loop/*` 进 adapter，达 T2.11 严格 zero legacy import。

> 并行执行：(A) rm 12 configs，(B) dispatch comprehensive fix implementer，(C) write memory。

句子的骨架已经是英文了。中文退化成了缝合线：一个"进"、一个"达"、一个"并行执行"的前缀——功能等同于语气词。像一个在美国长大、能听懂中文但组织语言全靠英文的 ABC（American-Born Chinese）。

这不是偶发。我们对 78 个含中文内容的 Claude Code 主对话做了系统性定量分析，经过四轮独立方法论审查，证实了这一现象。

## 单对话证据

### 对照例句

以下例句来自同一个 6 小时对话（167 条 assistant 文本消息），前后期**功能相同**——都是向用户汇报进度、描述下一步操作。

**前期**（msg 2，EN 52%）：
> State 核对完毕。active change 已就位（3 件套齐全），最近 commit 与 memory 一致，工作树仅几个未追踪 config 文件。现在用 TaskCreate 把剩余 11 项落成结构化清单。

"核对完毕"、"已就位"、"落成"——中文动词承载主要信息。英文只出现在专有名词。

**前期**（msg 45，EN 61%）：
> 明白，我误把并行 agent race 当成了 user 干预。让我核实当前 doc 状态再决定是否需要补做这些 sync edits。

"让我核实"、"再决定是否需要"——转折和决策逻辑用中文表达。

**后期**（msg 119，EN 93%）：
> Wave 2-γ ship 完整。Wave 2-δ：T2.6 network.py inline AZAgent (**关键 risk**)。Strategy: Option B inline-copy（保 legacy alive 给 core production 用，adapter 自身 inline），smoke verify r009 ckpt 能 load。

同样是汇报进度和决策，但"关键"两个字被包在英文句式里当修饰语用，"保……用"和"能 load"是中文壳包英文核。整段话的信息流是英文的。

**后期**（msg 136，EN 92%）：
> Dispatch ζ implementer：inline `legacy.config` + `legacy.train_loop/*` 进 adapter，达 T2.11 严格 zero legacy import。

"进"和"达"各一个字，像胶水一样粘在英文句子之间。去掉这两个字，整句话是合法英文。

**后期**（msg 116，EN 91%）：
> 143/143 pass，Wave 2-α + 2-β 全 ship + verified。下一步 Wave 2-γ：T2.1 mcts/ consolidate（1074 LOC，1 implementer，内部 sequential）。

"全"、"下一步"、"内部"——三个中文词散落在英文结构里。不是"中英混杂"，而是"英文写作，中文调料"。

上述例句都是 assistant **面向用户的沟通文本**——汇报进度、阐述策略、描述下一步操作。不是 git commit message，不是代码注释，不是工具输出。它们本应是中文，但写成了英文。

### 该对话的字符比例趋势

将 167 条消息按时间三等分，统计 ASCII 字母占（ASCII 字母 + CJK 汉字）的比例：

| 分段 | 英文占比 |
|---|---|
| 前 1/3（msg 1–55） | **74.3%** |
| 中 1/3（msg 56–110） | **81.4%** |
| 后 1/3（msg 111–167） | **87.3%** |

从 74% 单调递增到 87%，+13 个百分点。首十分位 70.0%，末十分位 86.7%，差值 +16.7 个百分点。

## 全局统计分析

### 数据集

从同一用户的 `~/.claude/projects` 中提取 712 个对话 JSONL（排除 cc-l10n 项目本身的对话），其中：
- 360 个含中文内容（CJK 字符 ≥ 10）
- 排除 subagent 对话（agent-\* 前缀，没有中文指令，天然全英文）后剩 86 个主对话
- 78 个满足分析最低要求（≥ 8 条 assistant 文本消息，CJK ≥ 30）

### 初始发现：字符比例指标

最初我们用 ASCII 字母占比（EN%）作为指标。结果：

- **82% 的对话斜率为正**（英文占比随对话推进上升）
- Sign test: **p < 0.0001**
- Wilcoxon signed-rank: **z = 4.909, p < 0.0001**
- 累计漂移率随长度递增：≥ 100 条消息的对话，70% 漂移；≥ 150 条，89% 漂移

### 方法论审查：字符比例不够

这套分析经受了独立审查（使用 Claude Opus 4.8 作为对抗性审查者，共四轮），发现两个关键问题：

1. **EN% 混淆了语言选择和技术术语密度**。一句正常的中文技术交流"需要 refactor 一下这个 module 的 interface"在 EN% 指标下被判为 75% 英文。但这是中文——只是夹了英文术语。
2. **任务阶段结构混淆**。编码对话天然从规划（中文讨论多）过渡到实现（代码/路径/commit 多），EN% 的上升可能反映的是任务阶段而非语言漂移。

因此我们设计了更严格的指标。

## 改进指标：word-run 长度

### 设计原理

不再数"有多少英文字符"，而是衡量**中文段和英文段各有多长**——直接反映句式结构。

分词规则：每个 CJK 字符 = 1 个 token，每个英文单词（连续 ASCII 字母）= 1 个 token。然后统计同类 token 连续出现的长度（word run）。

对比两种句子的 word-run 表现：

**中文句子夹英文术语**（不是漂移）：
```
"需要 refactor 一下这个 module 的 interface"
CJK runs = [2, 4, 1]    ← 中文段长度 2-4，仍有结构
ASCII runs = [1, 1, 1]   ← 英文段都是单词，没有连续英文句
```

**英文句子夹中文胶水词**（真漂移）：
```
"Dispatch implementer inline config 进 adapter 达 zero legacy"
CJK runs = [1, 1]        ← 中文退化为单字
ASCII runs = [4, 1, 2]   ← 英文形成多词连续句
```

这个指标免疫于"中文句子里多了几个英文术语"的干扰——术语增多不会改变中文段的长度，只有句式结构真正从中文变为英文时才会体现。

### 额外的文本清洗

为避免代码/标识符干扰，分析前剥离：fenced code blocks、inline code、XML 标签、URL、文件路径、camelCase/PascalCase/snake_case 标识符、dot.notation、hex hash。

### word-run 结果

在 78 个对话上的 per-conversation 斜率分析：

| 指标 | 漂移方向 | 符合方向的比例 | Sign test p | Wilcoxon p |
|---|---|---|---|---|
| 中文连续段平均长度 | 应下降 | **83%** 下降 | **< 0.0001** | **< 0.0001** |
| 英文连续段平均长度 | 应上升 | **76%** 上升 | **< 0.0001** | **< 0.0001** |
| 最长中文连续段 | 应下降 | **72%** 下降 | **0.0005** | **0.0006** |
| 中文段数量占比 | 应下降 | **73%** 下降 | **0.0002** | **0.0003** |

四个指标方向一致，全部 p < 0.001。

聚合归一化曲线（每个对话等权，归一化到 [0%, 100%] 进度）：

| 指标 | 开头 (0-20%) | 结尾 (80-100%) | 变化 |
|---|---|---|---|
| 中文连续段均长 | 34.8 tokens | 27.0 tokens | **-23%** |
| 英文连续段均长 | 1.77 tokens | 2.66 tokens | **+50%** |
| 最长中文连续段 | 67.8 tokens | 57.1 tokens | **-16%** |
| 中文段占比 | 0.55 | 0.50 | **-9%** |

### 与对话长度的关系

中文连续段均长的负斜率按长度分层：

| 长度 | N | 负斜率占比 | Sign test p |
|---|---|---|---|
| 8–19 | 16 | 69% | 0.106 |
| 50–99 | 12 | **92%** | **0.005** |
| 100–199 | 29 | **93%** | **< 0.001** |
| 200+ | 10 | **100%** | **0.002** |

200+ 消息的对话，**全部**表现出中文连续段缩短的趋势。

## 排除替代假说

### 替代假说：任务阶段效应

最强的替代解释是：编码对话天然从规划（中文散文多）过渡到实现（英文术语多），中文段缩短可能反映的是任务阶段变化而非语言漂移。

我们用三种方法排除这个假说。

#### 方法一：用户对照

如果漂移是任务阶段驱动的，同一对话中的用户消息也应该表现出相同趋势——毕竟用户也在经历相同的任务阶段。

结果（73 个有 ≥ 5 条用户文本消息的对话）：

| 指标 | 角色 | 趋势方向占比 | Wilcoxon p | 判定 |
|---|---|---|---|---|
| CJK run 长度 | **Assistant** | **82%** 下降 | **< 0.0001** | **显著漂移** |
| CJK run 长度 | User | 56% 下降 | 0.20 | **不显著** |
| ASCII run 长度 | **Assistant** | **75%** 上升 | **< 0.0001** | **显著漂移** |
| ASCII run 长度 | User | 40% 上升 | 0.99 | **完全不显著** |

聚合曲线：
- Assistant CJK run: 36.7 → 28.0（**-24%**）
- User CJK run: 13.3 → 12.2（**-8%，平坦**）

用户的语言结构**完全没有随对话进展变化**。同一个对话、同样的任务阶段推进——只有 assistant 的中文段在缩短，user 的没有。

用户全程用中文短指令交互，没有跟着模型切英文——用户在一个不断英文化的环境里坚持说中文，意味着如果用户也"放松"跟着模型用英文提问，漂移只会更快。

**对照局限**：审查者指出，用户消息天然是短指令（"继续"、"做吧"），文体全程稳定，不存在 register shift 的空间。因此用户对照排除了测量管线伪迹，但不能完全排除 register shift——因为用户消息本身就不会经历 register shift。

#### 方法二：段内斜率分析

如果漂移是任务阶段间的跳变（规划 → 实现 → 提交），那么在**同一阶段内部**，斜率应该为零。

把每个对话切三等分，在每段内部独立计算 CJK run 长度的线性斜率：

| 段 | N | 负斜率占比 | Wilcoxon p | 判定 |
|---|---|---|---|---|
| **前 1/3**（规划阶段） | 67 | **76%** | **0.0004** | **段内漂移显著** |
| 中 1/3（实现阶段） | 67 | 61% | 0.108 | 不显著 |
| 后 1/3（收尾阶段） | 67 | 60% | **0.042** | **段内漂移显著** |
| 整段 | 67 | **87%** | **< 0.0001** | — |

关键发现：**前 1/3 完全是规划阶段，没有任务阶段跳变——但 76% 的对话在此阶段内部就已经表现出 CJK run 缩短**（p = 0.0004）。

审查者评价：如果段内的子阶段变化（"理解问题 → 制定方案"）是驱动因素，需要 76% 来自不同项目的 67 个对话都有完全一致的子阶段顺序。这不可信。而且效应是连续的线性斜率，不是台阶形——子阶段跳变应该产生台阶函数。

#### 方法三：Between vs Within 分解

把总漂移分解为"段间跳变"（between，任务阶段效应）和"段内连续"（within，模型漂移）两个成分：

| 效应 | 负向占比 | Wilcoxon p | 判定 |
|---|---|---|---|
| Between（段间跳变） | 85% | < 0.0001 | *** |
| Within（段内连续） | 76% | 0.0001 | *** |

**两者都显著**。任务阶段效应是真实的叠加因素（between 显著），但无法解释全部——段内持续漂移同样显著（within 显著）。

### 四条证据线的收敛

将实际观测与两个假说的预测做对比：

| 预测 | 纯任务阶段假说 | 模型漂移假说 | 实际观测 |
|---|---|---|---|
| 段间跳变 (between) | 应显著 | 可能显著 | **显著 ✓** |
| 段内连续 (within) | 应 ≈ 0 | 应显著 | **显著 ✓** |
| 用户同步漂移 | 应一致 | 仅 assistant | **仅 assistant ✓** |
| 长对话末端更低 | 取决于阶段数 | 累积效应 | **120+ 比 60-119 低 ✓** |

观测在四项中的三项上排除了纯任务阶段假说。

### 同位置跨长度对比

在固定消息位置比较不同长度对话的 CJK run 值：

| 长度 | Pos 1–10 | Pos 11–20 | Last 10 |
|---|---|---|---|
| 60–119 (N=22) | 8.3 | 6.2 | **4.7** |
| 120+ (N=26) | 9.5 | 7.7 | **3.7** |

相同的起点位置（Pos 1–10），两组值相近（8.3 vs 9.5）。但末尾 10 条消息的差异明显：长对话的 CJK run 比短对话更短（3.7 vs 4.7）。这与累积漂移假设一致。

## 结论

**任务阶段效应是真实的叠加因素，但不能单独解释全部漂移。模型存在独立于任务阶段的持续语言漂移。**

经过四轮独立方法论审查（使用 Claude Opus 4.8 作为对抗性审查者），审查者给出的最终判定是：

> "The conclusion 'model-internal language drift exists' is supported by the evidence."
>
> Confidence: 82%.

18% 保留空间分配给：上下文语言分布拉动机制（~10%）、文本清洗可能的遗漏（~5%）、单用户数据的可推广性限制（~3%）。

## 为什么会漂移

Claude Code 的 system prompt 是英文，数千字的行为指引、工具描述、格式规范全是英文。末尾带一句 `Always respond in 简体中文`，但这条指令在对话中的"引力"会随上下文变长而被稀释：

1. **工具结果全是英文**——git 输出、文件内容、测试日志、task notification，都是英文。
2. **代码本身是英文**——变量名、commit message、分支名。
3. **system prompt 的其他数千字也是英文**——模型接收到的"语言环境"压倒性地指向英文。

一条 `Always respond in 简体中文` 在对话的第 3 条消息里还有效，到第 130 条就被周围的英文环境淹没了。模型的行为本质上是在对齐它所处的语言分布——而那个分布是英文主导的。

审查者指出的最强剩余假说：**上下文窗口内容组成效应**——随对话推进，上下文中累积了越来越多的英文内容（工具输出、代码、英文文档），模型的下一 token 分布被上下文中的语言分布拉动。这在技术上属于"模型内部行为"（模型对输入做出反应），但机制上不同于"模型自主放弃中文"——而是"模型被越来越英文化的上下文拉向英文"。不过，这个区别对用户来说没有实际差异：无论哪种机制，结果都是对话越长中文越少。

## 解法

[cc-l10n](https://github.com/RedContritio/cc-l10n) 走了一条不同的路：**直接把 Claude Code binary 内的英文 system prompt 替换为中文**。

不是 wrapper、不是 proxy、不靠 hook 在每轮注入"请说中文"的提醒。而是在 Bun standalone executable 的 JS payload 内原地替换字符串字面量，让模型从第一个 token 开始就身处中文环境。

当 system prompt 本身就是中文——工具描述是中文、行为指引是中文、格式规范是中文——模型的"语言环境"不再是英文主导的。那条 `始终用简体中文响应` 不再是大海里的一滴水，而是顺流。

```bash
git clone https://github.com/RedContritio/cc-l10n.git
cd cc-l10n
./cc-l10n install   # 自动定位 active binary，备份原版，替换中文版
```

三行命令。之后的长对话里，Claude Code 说的就是人话了。

## 局限性

1. **单用户数据**：所有对话来自同一用户，可能反映个人工作流模式。不同用户的漂移程度可能不同。
2. **文本清洗不完美**：尽管剥离了 code blocks、标识符、URL 等，仍可能有少量技术内容泄漏进分析。
3. **CJK 分词近似**：每个汉字视为一个 token（无分词器），与英文"每个空格分隔的词"为一个 token 的粒度不完全对等。
4. **上下文组成 vs 自主漂移**：当前分析无法完全区分这两种机制，尽管对最终用户而言效果相同。

## 方法论

### 核心指标：词游程长度

"游程"（run）是统计学标准概念：一个序列中，同一类别连续出现的一段叫一个游程。例如序列 `中中中英英中英英英` 有四个游程：`中中中`、`英英`、`中`、`英英英`，长度分别为 3、2、1、3。

我们对 assistant 消息的文本做如下处理：

1. **剥离非自然语言内容**：代码块、inline code、XML 标签、URL、文件路径、camelCase/PascalCase/snake_case 标识符、hex hash
2. **分词**：每个 CJK 字符（汉字）视为 1 个 token，每个连续英文字母序列（即一个英文单词）视为 1 个 token
3. **标记游程**：将 token 序列划分为"中文游程"（连续中文 token）和"英文游程"（连续英文 token）
4. **计算每条消息的指标**：中文游程平均长度、英文游程平均长度等
5. **对每个对话**：拟合指标随消息序号的线性斜率——即"这个对话里，中文游程长度是在变长还是变短"
6. **跨对话统计检验**：78 个对话各有一个斜率，检验这些斜率是否系统性地偏离零

用一个例子说明这个指标为什么能区分"正常技术交流"和"语言漂移"：

```
正常中文技术交流："需要 refactor 一下这个 module 的 interface"
  → 中文游程: [2, 4, 1]（"需要"、"一下这个"、"的"）
  → 英文游程: [1, 1, 1]（每个英文术语单独出现）
  → 中文游程均长 = 2.3，英文游程均长 = 1.0

语言漂移后："Dispatch implementer inline config 进 adapter 达 zero legacy"
  → 中文游程: [1, 1]（"进"、"达"各一个字）
  → 英文游程: [4, 1, 2]（英文形成多词连续句）
  → 中文游程均长 = 1.0，英文游程均长 = 2.3
```

如果只是在中文句子里夹了更多英文术语，中文游程仍然有长度（2-4 个字连续出现），英文游程只有长度 1（孤立的术语）。只有当句式结构真正从中文切换到英文——中文退化为单字胶水词、英文形成完整短语——中文游程长度才会下降、英文游程长度才会上升。

### 统计检验方法

本文使用的所有统计检验都属于"非参数检验"——不假设数据服从某种特定分布（如正态分布），适用于我们这种可能有异常值和偏态分布的数据。

以下对每种检验的解释假设读者没有统计学背景。

#### 什么是 p 值

p 值回答的问题是："如果漂移根本不存在（纯粹是随机波动），我观测到的结果有多大概率出现？"

- p = 0.05 意味着"如果无漂移，当前结果有 5% 概率出现"——通常被认为足够小，可以排除随机解释
- p = 0.001 意味着"0.1% 概率"——非常强的证据
- p < 0.0001 意味着"万分之一以下"——极强的证据

学术界通常以 p < 0.05 为显著性门槛。本文的核心结果远低于这个门槛。

#### Sign test（符号检验）

**问的问题**：78 个对话中，有多少个的斜率是负的（即中文游程在缩短）？这个比例显著高于"随机抛硬币"的 50% 吗？

**原理**：如果漂移不存在，每个对话的斜率正负应该是随机的——像抛硬币一样，大约 50% 正、50% 负。实际观测到 83%（65/78）为负。用二项分布计算：78 次抛硬币出现 65 次以上正面的概率 < 0.0001。

**优点**：只看方向，完全不受异常值影响。即使有几个对话的斜率极端大或极端小，也不影响结果。

**缺点**：丢弃了"斜率有多大"的信息，统计功效（检测真实效应的能力）较低。

#### Wilcoxon signed-rank test（Wilcoxon 符号秩检验）

**问的问题**：78 个斜率的分布是否系统性地偏离零？不仅看方向（正/负），还看相对大小。

**原理**：
1. 把 78 个斜率按绝对值从小到大排序，赋予秩（排名）1 到 78
2. 把负斜率的秩加在一起，得到 W⁻；正斜率的秩加在一起，得到 W⁺
3. 如果无漂移，W⁺ 和 W⁻ 应该大致相等。如果负斜率不仅更多、而且绝对值也更大（秩更高），W⁻ 就会远大于 W⁺

**优点**：比 Sign test 更强——同时利用了方向和大小信息。通过"秩"（排名）而非原始值来衡量大小，对异常值有较强的抵抗力。

**缺点**：仍然可能受极端异常值的轻微影响（因为极端值获得最高的秩）。

**Sign test + Wilcoxon 都显著意味着**：不仅是大多数对话方向一致（Sign），而且负斜率在幅度上也系统性地大于正斜率（Wilcoxon）。

#### Mann-Kendall trend test（Mann-Kendall 趋势检验）

**问的问题**：一个对话内部，中文游程长度是否有单调递减趋势？

**原理**：对该对话的所有消息对 (i, j)（i 在 j 之前），统计"后面消息的值比前面大"出现了多少次、"后面比前面小"出现了多少次。如果递减趋势存在，"后面比前面小"的次数应该远多于"后面比前面大"。

**与前两个检验的区别**：Sign test 和 Wilcoxon 是**跨对话**的检验（每个对话贡献一个数据点）；Mann-Kendall 是**对话内部**的检验（在一个对话的消息序列上检测趋势）。

**在本文中的使用**：对 78 个对话分别做 Mann-Kendall 检验，然后统计有多少个对话检测到显著的上升/下降趋势。

#### Permutation test（排列检验 / 置换检验）

**问的问题**：一个对话内部，消息的时间顺序是否重要？如果把消息顺序打乱，观测到的斜率还会这么大吗？

**原理**：
1. 计算该对话消息按真实顺序排列时的斜率
2. 把消息顺序随机打乱 2000 次，每次重新计算斜率
3. 看真实斜率在 2000 个随机斜率中排第几——如果排在最极端的 5% 以内，说明真实顺序下的趋势不太可能是巧合

**优点**：不依赖任何数学分布假设，完全由数据自身决定。

**缺点**：计算量大（每个对话要洗牌 2000 次）。

#### 段内斜率分析（Within-segment analysis）

**问的问题**：如果把对话按时间切成三段（前 1/3、中 1/3、后 1/3），在每一段**内部**是否也存在递减趋势？

**原理**：这是用来区分"任务阶段跳变"和"持续漂移"的关键检验。

- 如果漂移只是因为任务从"规划"跳到"实现"再跳到"提交"，那变化应该发生在段与段**之间**（台阶形），每段**内部**应该是平的
- 如果漂移是模型的持续行为，那每段内部也应该有递减趋势

实际操作：对每段内部单独拟合斜率，然后对这些段内斜率做 Sign test 和 Wilcoxon。

#### Between-Within 分解

**问的问题**：总漂移中，有多少来自段间跳变（任务阶段效应），有多少来自段内连续漂移（模型行为）？

**原理**：
- **Between 效应**：最后一段的平均值 - 第一段的平均值。反映段间跳变的大小。
- **Within 效应**：三段内部斜率的平均值。反映段内持续漂移的速率。
- 分别对这两个量做 Sign test 和 Wilcoxon。

如果只有 Between 显著、Within 不显著 → 纯任务阶段效应。
如果 Within 也显著 → 模型存在独立于任务阶段的持续漂移。
